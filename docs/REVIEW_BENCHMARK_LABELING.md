# Review benchmark labeling rules

## Purpose

Before Deploy benchmark labels are reviewed evaluator data. They are not generated by an LLM, do not inherit release authority from a deterministic control, and do not become policy simply because they appear in a benchmark corpus.

The label set exists to measure advisory discovery quality reproducibly.

## Label eligibility

A source case may enter the maintained corpus only when all of the following are true:

1. the source bytes are version controlled and pinned in the corpus manifest;
2. the vulnerable behavior has a concrete, human-readable rationale;
3. an existing regression test independently establishes the behavior used as provenance;
4. a repository-relative path and stable source range can be assigned without executing untrusted fixture code;
5. the label uses the canonical advisory category and severity vocabulary.

A deterministic control finding may support a label, but deterministic finding count does not automatically determine benchmark label count.

## Unit of labeling

The benchmark labels one **review issue/root cause**, not one scanner event.

When adjacent statements express the same root cause, they may be represented by one contiguous label range. For example, two adjacent destructive SQL statements without predicates are one root-cause benchmark issue in seed v1 even though the deterministic control emits two findings. This avoids making the benchmark circular with the implementation details of one scanner.

Separate independently actionable root causes should receive separate IDs.

## Source anchors

Use the narrowest contiguous source range that contains the review issue. Prefer the sink or decision point over a whole function when the smaller anchor is sufficient.

Every maintained source file is pinned by its exact Git blob SHA-1 in the manifest. The validator recomputes the Git object identifier from repository bytes and fails on drift. The identifier is a reproducibility mechanism only; it is not an authenticity or collision-resistance claim.

When source bytes change, the label must be re-reviewed. Update the blob identifier and source range in the same reviewed change.

## Positive and negative sources

The manifest distinguishes:

- `positive` files, each of which must contain at least one labeled defect;
- `negative` files, which are intentionally in evaluation scope but contain no maintained defect label for the tested contract.

Paired secure fixtures are preferred because they make false-positive behavior observable rather than measuring recall alone.

The seed v1 validator requires the set of positive paths to equal the set of paths referenced by corpus defects. A negative path may not carry a label.

## Category vocabulary

Corpus categories must use the same canonical values accepted by normalized advisory findings:

- `bug`
- `security`
- `performance`
- `maintainability`
- `test`
- `style`
- `documentation`
- `other`

Seed v1 is intentionally security-focused. Later corpus versions may add other categories only through reviewed labels and the same provenance contract.

## Severity vocabulary

Optional severity metadata must be one of:

- `critical`
- `high`
- `medium`
- `low`
- `info`

Severity does not participate in v1 matching and does not map to deterministic gate authority.

## Evidence-test provenance

Every label cites one existing test selector in the form:

```text
path/to/test_file.py::test_function_name
```

The cited test must exist and independently exercise the behavior behind the label. Corpus validation verifies that both the test file and named test function still exist.

The test is provenance, not an automatic label generator. Human review owns the mapping from the tested behavior to the benchmark issue, category, severity, and line range.

## Leakage and evaluator separation

Provider input for a corpus is limited to source files explicitly listed in `manifest.json.files` plus future bounded context selected under the provider/context contract.

Evaluator-only material must not be included in provider context:

- ground-truth labels;
- corpus manifest rationale;
- oracle advisory output;
- benchmark reports;
- this labeling guide.

A run that exposes evaluator-only data to the reviewer is contaminated and must not be reported as a valid benchmark result.

## Label changes and adjudication

Any addition, deletion, category change, range change, or rationale change is a normal reviewed code change. The change must update provenance as necessary and keep corpus validation green.

Disputed labels are resolved by reviewing the source behavior and the cited regression evidence. Model agreement, provider confidence, or benchmark score is not sufficient evidence to add or remove ground truth.

## Reporting limits

The seed corpus is deliberately too small and too security-focused to support broad claims such as “best code reviewer.” Any published result must identify at least:

- corpus name/version;
- provider and model/runtime identifier;
- provider configuration and context contract when available;
- date or source revision;
- precision, recall, F1, and raw TP/FP/FN counts.

Benchmark measurements remain diagnostic and cannot approve a release.
